# CallTracer

**本番環境のまま、JavaScriptとPythonの実行フローを1本のタイムラインで可視化する、管理者専用デバッグツール**

自分が開発・運用しているWebアプリ(Flask/FastAPI + フロントエンド)に組み込んで使う、常設のデバッグ支援ツールです。「ローカル環境を用意しなくても、今まさに本番で動いているリクエストの中身を見たい」という実運用上のニーズから生まれました。

---

## 何ができるか

ブラウザで管理者用ページを開き、対象アプリを操作すると、以下が1本のタイムラインとしてリアルタイムに表示されます。

![alt text](<スクリーンショット 2026-07-28 142428.png>)

- ボタンクリック(JS)
- fetch()によるAPI呼び出し(JS)
- サーバー側の関数呼び出し階層(Python)
- 外部API(Supabase等)への通信

これらが、実際に呼ばれた順番・ネストの深さがひと目でわかる形で並びます。

## なぜ作ったか

開発中、「どのボタンを押すと、サーバー側でどの関数が、どんな順番で呼ばれているのか」を把握するのに、ログを行ったり来たりして追うのが非効率だと感じたのがきっかけです。最初はローカル開発専用のCLIツールとして作り始めましたが、「本番で実際に起きている問題を、その場で追いたい」という要求に応えるため、**本番環境に常設できる、認証保護された管理者専用ツール**として設計し直しました。

## アーキテクチャ

```
[管理者のブラウザ]                    [対象アプリ(Flask/FastAPI、Render等)]
  inject.js が fetch/click を横取り
    → 実リクエストに X-CallTracer-Session,
      X-CallTracer-Request-Id ヘッダーを付与
    → 通常通りAPIを呼ぶ
                                    ┌─ ミドルウェア: ヘッダーを見てcontextvarに
                                    │   session_id/request_idをセット
                                    │   (このリクエストの間だけ)
                                    │
                                    ├─ sys.settrace ベースのトレーサー
                                    │   (管理者セッションが1つも無い間は
                                    │    完全に無効化。有効時のみ全関数
                                    │    呼び出しをチェックする設計)
                                    │
                                    └─ /__calltracer__/poll (ポーリング)
                                        管理者のViewerが1秒おきに取得
```

### 主要コンポーネント

| モジュール | 役割 |
|---|---|
| `core/tracer.py` | `sys.settrace`ベースのPython呼び出しトレーサー。`contextvars`でスレッド/asyncioタスクごとに呼び出し深さを分離 |
| `core/session.py` | 管理者セッションの発行・有効期限管理 |
| `core/event_bus.py` | セッションIDごとのイベントキュー |
| `integrations/flask_adapter.py` / `fastapi_adapter.py` | Flask/FastAPIそれぞれへの薄い統合レイヤー |
| `static/inject.js` | `fetch`・クリックイベントを横取りし、サーバーへ報告するクライアントスクリプト |
| `static/timeline.html` | 管理者用Viewer画面 |

## 技術的な特徴

- **対象アプリへの変更は最小限**: `init_flask(app, is_admin=...)` を1回呼ぶだけで組み込める
- **既存の認証をそのまま利用**: CallTracer自体は認証ロジックを持たず、`is_admin(request) -> bool` という関数を渡すだけで、JWTでもセッションでもAPIキーでも対応可能
- **「見ている間だけ」トレース**: 管理者セッションが有効な間だけ`sys.settrace`を有効化し、無関係な一般ユーザーのリクエストは一切トレース対象にしない設計
- **依存ライブラリがほぼゼロ**: Flask/FastAPI自体以外の追加ライブラリを必要としない

## 開発中に直面した技術的課題と解決(抜粋)

ポートフォリオとして特に見てもらいたい、実運用で初めて表面化した問題とその対処です。

1. **Gunicornのsyncワーカーとの相性問題**
   当初SSE(Server-Sent Events)で実装したところ、本番(Render + Gunicorn)で`WORKER TIMEOUT`が頻発。Gunicornのsyncワーカーが「長時間ブロックする接続」を反応の無いワーカーと誤検知し、強制終了・再起動させてしまうことが実機ログから判明。ワーカー再起動のたびにセッション情報(プロセスメモリ上で管理)が消える不具合の根本原因だった。→ SSEを廃止し、1秒間隔のポーリング方式に設計変更。

2. **クロスオリジン環境でのセッション共有**
   フロントエンド(Vercel)とバックエンド(Render)が別ドメインの場合、`localStorage`はドメインごとに分離されているため、Viewerが発行したセッションIDをフロントエンド側から読み取れない問題があった。→ URLクエリパラメータ経由でセッションIDを引き継ぐ仕組みを追加。

3. **標準ライブラリの疑似パスによる誤トレース**
   `<frozen ntpath>`のような、実ファイルではない疑似パスに`os.path.abspath()`を適用すると、たまたま監視対象ディレクトリ配下に見える文字列が生成されてしまい、標準ライブラリの内部実装まで誤ってトレース対象になるバグを発見・修正。

4. **異なるマシンの時計に依存しない順序保証**
   ブラウザ(JS側)とサーバー(Python側)は別々の時計を持つため、`timestamp`だけを頼りに並べ替えると、クロックのズレで表示順序が乱れることがあった。→ JS側で発行した`request_id`をHTTPヘッダー経由でサーバーに伝搬させ、同じ操作に属するイベントをID単位でグループ化。グループの並び順は同一クロック(ブラウザ側)を基準にすることで、マシン間の時計のズレに影響されない表示順序を実現。

5. **ブラウザAPIの制約に合わせた認証設計**
   `EventSource`や`<script>`タグはカスタムヘッダーを送信できないため、これらのエンドポイントを`is_admin`のヘッダーチェックで保護することができない。実際のセキュリティ境界を「`fetch()`経由でカスタムヘッダーを送れる`/session/start`」だけに絞り、以降は推測不可能なセッションIDを通行証として扱う設計に整理した。

## 既知の制約

- `sys.settrace`はプロセス単位の設定のため、複数ワーカープロセス構成では、管理者のセッション状態がワーカーごとに独立してしまう
- FastAPI/Starlette統合は設計・実装済みだが、開発環境の制約により実機での動作確認は未実施
- ブラウザの言語仕様上、JavaScript側は「関数呼び出し全部」を横取りする仕組みがなく、`fetch`とクリックイベントに限定して可視化している
